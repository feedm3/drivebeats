# Metadata implementation and verification

Status: local implementation and sampled acceptance completed, 22 October 2026. Static reviews, repository validation, and observed browser behavior are recorded separately. Wider device, cross-session, and deployed-host acceptance remains open.

## Implemented behavior

- One account-, content-version-, parser-, and policy-scoped local metadata cache serves the UI, playback, local search, and page WebMCP. IndexedDB stores successful text tags, confirmed absence of target tags, and deterministic unresolved outcomes. Transient failures have separate retry state. Explicit logout fences pending work and clears local data; a cold offline session can use its remembered local account's existing tags and version-matched audio without granting remote access.
- One shared loader validates known Library or collection membership before reading and before publishing. It shares work and cancellation across consumers, reuses available playback/offline audio, and otherwise performs bounded sparse reads with the installed jsmediatags parser. Filename/folder display fallbacks remain separate from extracted tags.
- Drive transport is prioritized and coordinated across browser callers/tabs. Transfer ownership lasts through body consumption or cancellation. Playback has priority; unnecessary work can yield. Budget windows, cooldown, leadership, and progress survive supported reload/tab transitions; degraded coordination is reported rather than presented as a global guarantee.
- Automatic work starts with visible tracks, then the Current Folder and proven Library. Catalog construction and metadata work share bounded scheduling. Local searches use cached text without media downloads; immutable bounded cursor snapshots preserve tag values and ordering during normal cache warming. Status/coverage distinguishes checked, unresolved, stale, error, and unknown tracks. The ordinary UI has a small activity/details surface rather than index-management controls.
- Extracted tags no longer upload to or hydrate from Neon. Playlists and Favorites retain their collection/file descriptors and normal collection sync. Legacy tag-upload compatibility is retired safely. Deferred SQL outside the active migration directory prepares the eventual `track_metadata` drop; migration `0006` is preserved. No destructive migration has been executed.

Implementation details and provisional limits remain grounded in the [reviewed plan](research/id3-metadata-plan.md). The [handover](research/id3-metadata-handover.md) preserves the earlier planning/review history; its original intake-only instructions and historical test results must not be mistaken for current implementation acceptance.

## Approved transport change

The authenticated browser returned a valid 16-byte Google media `206`, but Google did not expose `Content-Range` to page JavaScript. The direct reader correctly rejected an unverifiable range. The user then explicitly approved a bounded same-origin endpoint, replacing the plan's original prohibition on an automatic server-proxy fallback.

The metadata path now uses `POST /api/auth/drive-range` explicitly. It checks same-origin request headers, the signed session and Drive scope, and the requested account. Server-side OAuth refresh and an OpenID userinfo check bind the refreshed token to that signed account before one upstream media GET. Input is capped at 4 KiB, each range at 1 MiB, and a combined 12-second deadline covers request parsing and upstream work. Exact `206`, range/size, and actual body length are required; unexpected full responses are cancelled. There are no server media retries, full-file fallbacks, media persistence, or token/tag logging. OAuth refresh and userinfo are additional non-Drive provider requests, distinct from the browser's Drive request allowance.

Tags still parse and persist in the browser. Policy version 2 and the transport environment key invalidate earlier direct-CORS unresolved results. The endpoint authorizes the user's Google app-accessible file capability; Library ancestry remains a browser-local proof. Browser scheduling is not a server-wide abuse or concurrency limit. See [endpoint boundaries](metadata-range-endpoint.md).

### Limits, priority, and speed

A persisted per-track reader limit means that track is skipped as unresolved and other tracks continue. Shared background allowance exhaustion pauses work until its two-minute window resets; provider cooldowns honor their retry timing. Consumer/tool-batch deferrals remain retryable and do not become permanent content failures. Visible rows take priority, then the current folder, then the remaining proven Library. This changes order, not allowance. Cached navigation can wait for the current job; an actual foreground listing can preempt it. Priority is based on the active indexing leader's local viewport, not a broadcast of every tab's viewport.

The unchanged conservative background policy allows 50 Drive reads and 5 MiB per 120 seconds, with one transfer at a time and request spacing. Parallelism cannot overcome that sustained cap. The implemented small optimization fixes jsmediatags to its ID3v2 reader only after validating an ID3v2 header, avoiding an unnecessary 128-byte tail detection read. ID3v1/tagless fallback remains available. Normal ID3v2 tracks now need two sparse reads plus two descriptor checks: four Drive GETs rather than five. Large embedded artwork still counts even when only text fields are requested. Legacy Drive-range `budget_exceeded` results become stale once under a dedicated strategy revision; successful tags and other outcomes retain their cache validity.

At that request cap alone, 2,000 ordinary four-read tracks require roughly 5 h 20 min of eligible active indexing time, versus 6 h 40 min at five reads. This is arithmetic, not a measured completion ETA: bytes, latency, hidden tabs, navigation, playback, and retries can increase it. A 39-case synthetic experiment against the installed parser compared ID3v2.2/2.3/2.4, cover artwork, boundary sizes, and fallback behavior before implementation. Larger prefixes, removing version checks, increasing budgets, token caching, and parallel metadata lanes were evaluated but are not implemented.

Google's published quota model changed in May 2026 and older projects can retain earlier allocations. The actual DriveBeats project's effective quota and the exact unit classification of Range media calls were not confirmed. No quota increase is justified by assumed defaults. Primary sources: [Drive limits](https://developers.google.com/workspace/drive/api/guides/limits), [partial downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads).
